# 获得补丁释放 {#get-a-fix-into-a-patch-release}

一旦发布出来,新的功能等待下个月. 错误修正不必。 在β周,修复进入下一个β. 发布后,他们进入每周补丁发布.

## 工作原理 {#how-it-works}

所有修正都从正常方式开始 : a pull request 对 `dev` 分支 。 目标没有单独的分支,您无需打开第二个 pull request 。

当一个固定器应该进入β或下一个补丁发布时,pull request会被添加到该版本在GitHub上的里程碑上,就像`2026.11.1`. 发行团队在准备β或补丁发行时,会将该里程碑中每个合并的pull request,并将其更改复制到发行分支中. 这叫摘樱桃 pull request然后得到`cherry-picked`的标签,所以你可以看到它成功。

Adrian. 在发行笔记中,β周期间选择的修饰标记为β修饰.

## 选什么? {#what-gets-picked}

补丁发布只包含错误修正, 绝不包含特性 。 释放小组逐案决定,这些事情使得更可能选择固定:

- 它修正了一个倒退:在前一次发行中起作用的东西,在这个版本中破裂了.
- 它可以修复一个影响很多人的虫子,或者打破一些重要的东西.
- 它用这个发行的新集成或特征来解决一个问题.
- 它很小而且安全。 补丁释放不应该打破别的东西.

对错误进行修复的依赖性更新,或者因为服务更改了其API而需要的,也可以选择.

## 你可以做点什么 {#what-you-can-do}

- 说在pull request。 解释它解决了哪一个问题,并解释它是一种倒退或影响目前的释放。 将问题联系起来。
- 保持小的固定点。 ** 专注的修补是容易审查的,也是容易挑选的. 与重构混合的固定不是。
- ** 请求。 ** 如果您认为一个合并的修饰应该在下一个补丁发布中,请在pull request中提及,并询问整合或发布团队的维护者. 当回答是"下个月"时,不要以个人为己任:释放团队权衡每一个选择,以抵挡破坏别的东西的风险.

## 谁决定 {#who-decides}

维护者和释放小组决定什么是里程碑。 发行团队负责选樱桃并发布发行. 见[谁做什么?](/releases/reference/roles).
